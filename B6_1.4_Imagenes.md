## B6.1.4 — Imágenes: `pull`, `images`, `rmi`. ¿Dónde vive lo que descargas?

> [!abstract] Ficha de la práctica

> [!info] Caso real (contexto profesional)
> El servidor de la empresa se queda sin espacio. Nadie ha subido ficheros grandes y los logs están rotados. El culpable resulta ser `/var/lib/docker`: **meses de imágenes descargadas y nunca borradas**. Es una de las causas más habituales de disco lleno en servidores con contenedores, y una de las más fáciles de prevenir si sabes dónde mirar.

- **🎯 Objetivo real:** gestionar el almacén local de imágenes: descargar, listar, medir lo que ocupan de verdad y borrar lo que sobra.
- **🧩 Problema que resuelve:** las imágenes se acumulan en silencio. Si no sabes dónde viven ni cómo medirlas, te enteras cuando el servidor se para.

---

## 📚 Fundamento

> [!info] Dónde vive todo esto
> Todo lo que descarga Docker se guarda en **`/var/lib/docker`**, en el disco de tu servidor. No se instala en el sistema como haría `apt`: se queda ahí, aparte, esperando.
>
> Esa carpeta **es propiedad de root y no se toca a mano jamás**. Se gestiona con los comandos de Docker. Borrar cosas ahí dentro con `rm` es la forma más rápida de corromper la instalación entera.

> [!warning] El fallo nº1: sumar la columna SIZE de `docker images`
> Ejecutas `docker images`, ves cinco imágenes de 200 MB y concluyes que ocupan 1 GB. **Casi seguro que es falso.**
>
> Recuerda las **capas** de B6.0.3: las imágenes comparten capas, y una capa compartida **se guarda una sola vez**. La columna `SIZE` muestra el tamaño *lógico* de cada imagen —contando sus capas compartidas— así que sumarla cuenta lo mismo varias veces.
>
> **El dato real lo da `docker system df`.** Es el comando que tienes que usar cuando alguien te pregunte cuánto ocupa Docker.

> [!example] Vocabulario de esta práctica
> - **`docker pull`:** descarga una imagen **sin** crear ningún contenedor.
> - **`docker images`:** lista las imágenes que tienes en local.
> - **`docker rmi`:** borra una imagen (*remove image*). **No confundir con `docker rm`**, que borra contenedores.
> - **`docker system df`:** el uso de disco **real** de Docker.
> - **Imagen huérfana (`<none>`):** imagen sin etiqueta, normalmente sustituida por una versión más nueva. Ocupa y no sirve.
> - **`docker image prune -a`:** borra de golpe **todas** las imágenes sin contenedor que las use. Potente y peligroso: lo que borra hay que volver a descargarlo.

## 🛠️ Procedimiento

> [!example] Paso 0 — Prepárate y empieza a grabar
> Arranca OBS y preséntate. Parte de un sistema limpio y anota el espacio libre inicial:
> ```bash
> docker ps -a
> docker images
> df -h /var/lib/docker
> ```

> [!example] Paso 1 — Descarga sin ejecutar
> ```bash
> docker pull alpine
> docker images
> docker ps -a
> ```
> **Tienes la imagen pero ningún contenedor.** `pull` solo descarga. Es la prueba definitiva de que imagen y contenedor son cosas distintas.
>
> Apunta el tamaño de `alpine`: unos **13 MB**. Es la distribución mínima que ya usaste en B6.2.1.

> [!example] Paso 2 — Descarga una imagen CONSTRUIDA SOBRE la anterior
> `nginx:alpine` es Nginx montado encima de esa misma Alpine. Es decir: **comparte su capa base**.
> ```bash
> docker pull nginx:alpine
> ```
> Mira la salida con atención. Si tu Docker usa el almacén clásico, verás alguna línea **`Already exists`**: esa capa ya la tenías de `alpine` y **no se vuelve a descargar**.
>
> > ℹ️ Según la versión y el almacén de imágenes de tu Docker, puede que **no** aparezca el texto `Already exists`. No te preocupes: el Paso 3 demuestra el ahorro con números, y ese funciona siempre.

> [!example] Paso 3 — La medición honesta (el entregable importante)
> ```bash
> docker images
> docker system df
> ```
> **Haz la cuenta a mano y compárala:**
>
> | | |
> |---|---|
> | `alpine` según `docker images` | ~13 MB |
> | `nginx:alpine` según `docker images` | ~93 MB |
> | **Suma** | **~106 MB** |
> | **Lo que dice `docker system df`** | **~93 MB** |
>
> **Faltan unos 13 MB: justo el tamaño de Alpine.** No es un error de la herramienta: es que la capa base **se guarda una sola vez** y las dos imágenes la comparten.
>
> **Anota los dos valores y explica la diferencia en voz alta en el vídeo.**

> [!example] Paso 3b — La prueba definitiva: mira las capas una a una
> Si quieres verlo sin margen de duda, pregunta por las capas de cada imagen:
> ```bash
> docker inspect alpine --format '{{range .RootFS.Layers}}{{println .}}{{end}}'
> docker inspect nginx:alpine --format '{{range .RootFS.Layers}}{{println .}}{{end}}'
> ```
> `alpine` tiene **una** capa. `nginx:alpine` tiene **ocho**, y **la primera es exactamente la misma** (mismo `sha256`). Ahí está la prueba de que se reutiliza.
>
> Compáralo ahora con dos imágenes que **no** comparten nada:
> ```bash
> docker pull nginx:1.26
> docker pull nginx:1.27
> docker system df
> ```
> Suma sus tamaños y mira el total: aquí **no hay ahorro**, porque entre esas dos versiones cambió la base y no comparten ni una capa. **Compartir capas no es automático: depende de cómo esté construida la imagen.**

> [!example] Paso 4 — La etiqueta importa
> ```bash
> docker images nginx
> ```
> Del paso anterior tienes `nginx:alpine`, `nginx:1.26` y `nginx:1.27`: **mismo nombre, distinta etiqueta, imágenes diferentes**. Ahora:
> ```bash
> docker pull nginx
> docker images nginx
> ```
> Acabas de bajarte **una más: `nginx:latest`**. Compruébalo. Es la trampa de `latest` que viste en B6.0.3: pediste "nginx" a secas y te has llevado otra imagen distinta, ocupando disco.

> [!example] Paso 5 — `rm` frente a `rmi`
> ```bash
> docker run -d --name prueba nginx:1.26
> docker rmi nginx:1.26
> ```
> **Falla:** `conflict: unable to delete nginx:1.26 (must be forced) - container ... is using its referenced image`. Docker no te deja borrar una imagen que un contenedor está usando. Correcto:
> ```bash
> docker rm -f prueba
> docker rmi nginx:1.26
> docker images
> ```
> **La imagen se ha ido, pero fíjate:** si la vuelves a necesitar, se descarga otra vez. Borrar la imagen es distinto de borrar el contenedor.

> [!example] Paso 6 — Dónde vive (mirar, no tocar)
> ```bash
> sudo du -sh /var/lib/docker
> sudo ls /var/lib/docker
> ```
> Ahí está todo: imágenes, capas, contenedores y volúmenes.
>
> ⚠️ **Míralo y no toques nada.** Se gestiona con los comandos de Docker, nunca con `rm`.

> [!example] Paso 7 — Limpieza profesional (selectiva, que es como se hace)
> Después del Paso 5 te quedan tres imágenes de Nginx: **`alpine`**, **`1.27`** y **`latest`**. Mide, borra la que ya no necesitas y vuelve a medir:
> ```bash
> docker system df
> docker images nginx
> docker rmi nginx:1.27
> docker system df
> ```
> **Compara el antes y el después** y di en el vídeo cuánto espacio has recuperado. Fíjate en que el número recuperado es **menor** que el `SIZE` que mostraba `docker images` para esa imagen: las capas que compartía con `nginx:latest` siguen en disco, porque esa se queda. Es la teoría de las capas, otra vez, medida por ti.
>
> ⚠️ **Deja `nginx:latest` y `alpine` en el sistema.** Son las que usarás en toda la Fase B6.2, y si las borras tendrás que descargarlas de nuevo.

> [!danger] El comando grande, y por qué hoy NO lo vas a ejecutar
> Existe un comando que borra de golpe **todas** las imágenes que no esté usando ningún contenedor:
> ```
> docker image prune -a
> ```
> Es el que verás en cualquier guía de limpieza, y funciona. Pero tiene dos consecuencias que hay que conocer **antes** de teclearlo:
>
> 1. **Se lleva todo lo que no esté en uso en ese instante**, incluidas imágenes que te harán falta dentro de cinco minutos. Todo lo que borre hay que **volver a descargarlo**.
> 2. En un aula con veinte personas haciendo lo mismo a la vez, esa segunda descarga sale por la misma línea de internet del centro. Multiplica y ya tienes la clase parada.
>
> Por eso aquí limpiamos **con nombre y apellidos** (`docker rmi imagen:etiqueta`). `prune -a` es para cuando cierras un proyecto y sabes que no vas a volver, no para el mantenimiento del día a día.

> Detén OBS, nombra el vídeo **`B6.1.4 · Imágenes, dónde vive lo que descargas`**, súbelo a **`B6_Contenedores`** y añade timestamps.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Sumar la columna `SIZE` | Das un dato falso e inflado | Usa **`docker system df`** para el tamaño real. |
> | Confundir `rm` con `rmi` | Borras lo que no querías | `rm` = contenedor · `rmi` = **i**magen. |
> | Borrar a mano en `/var/lib/docker` | Instalación corrupta | Solo con comandos de Docker. **Nunca con `rm`.** |
> | Lanzar `prune -a` para "hacer limpieza" | Borras imágenes que necesitas en la siguiente práctica y hay que bajarlas otra vez | Limpia **con nombre y apellidos**: `docker rmi imagen:etiqueta`. |
> | Trabajar siempre con `latest` | Acumulas versiones sin saberlo | Etiqueta explícita en todo lo que dure. |
> | No revisar el disco periódicamente | Servidor lleno sin motivo aparente | `docker system df` en tu rutina de mantenimiento. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - Sabes descargar una imagen **sin** crear contenedores.
> - Has medido el ahorro real: la suma de `SIZE` es mayor que el total de `docker system df`.
> - Has comprobado con `docker inspect` que `alpine` y `nginx:alpine` **comparten la primera capa**.
> - Sabes decir cuánto ocupa Docker **de verdad** y por qué no es la suma de `SIZE`.
> - Has visto fallar `docker rmi` sobre una imagen en uso.
> - Distingues `rm` de `rmi` sin dudar.
> - Sabes dónde vive todo y **por qué no se toca a mano**.
> - Has recuperado espacio borrando una imagen concreta, y `nginx:latest` **sigue en el sistema** para la Fase B6.2.

> [!question] Comprueba que lo has entendido
> 1. ¿Qué diferencia hay entre `docker pull nginx` y `docker run nginx`?
> 2. `alpine` ocupa 13 MB y `nginx:alpine` 93 MB, pero juntas ocupan 93 MB en disco, no 106. Explica por qué.
> 3. Tienes 4 imágenes de 300 MB en `docker images`. ¿Puedes afirmar que Docker ocupa 1,2 GB? Razónalo y di qué comando usarías.
> 3b. `nginx:1.26` y `nginx:1.27` **no** comparten ninguna capa, pero `alpine` y `nginx:alpine` **sí**. ¿De qué depende que dos imágenes compartan capas?
> 4. Explica la diferencia entre `docker rm` y `docker rmi` con un ejemplo de cada uno.
> 5. ¿Por qué Docker impide borrar una imagen que usa un contenedor en marcha?
> 6. Un servidor de la empresa se ha quedado sin disco. Describe los tres comandos que ejecutarías, en orden, para diagnosticarlo y resolverlo.
