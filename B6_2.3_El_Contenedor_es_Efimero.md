## B6.2.3 — El contenedor es efímero: escribe, borra, desaparece

> [!abstract] Ficha de la práctica
> ### 📌 `B6.2.3` — El contenedor es efímero
> - **Bloque 6** (Aislamiento de servicios) · **Fase B6.2** (Mirar dentro) · **Nivel 1** (Básico) · **RA.01** · **CE.01.b · CE.01.e**
> - **🎬 Playlist:** `B6_Contenedores`
> - **📹 Nombre del vídeo:** `B6.2.3 · El contenedor es efímero`
> - **Requisito previo:** [[B6_2.2_Procesos_Dentro_y_Fuera|B6.2.2]] y el concepto de **capa de escritura** de [[B6_0.3_Vocabulario|B6.0.3]].

> [!info] Caso real (contexto profesional)
> Un técnico levanta una base de datos en contenedor "para probar". Funciona. La deja en producción sin tocar nada más. Meses después recrea el contenedor para actualizar la versión y **pierde todos los datos de la empresa**.
>
> No fue un fallo de Docker. Fue no entender lo que vas a ver hoy.

- **🎯 Objetivo real:** comprobar **experimentalmente** qué sobrevive y qué no, y distinguir con precisión entre parar y borrar.
- **🧩 Problema que resuelve:** es el error más caro que se comete con contenedores, y el que justifica toda la fase B6.4.

## 📚 Fundamento

> [!info] La capa de escritura, ahora en la práctica
> Recuerda B6.0.3: la imagen son capas de **solo lectura**, y al arrancar un contenedor se le añade **una capa de escritura propia**.
>
> Todo lo que el contenedor cree o modifique vive ahí. Y esa capa **pertenece al contenedor, no a la imagen**.
>
> ```mermaid
> flowchart TB
>     I["🖼️ IMAGEN nginx — capas de SOLO LECTURA<br/>(sobreviven a todo)"]
>     W["✏️ Capa de escritura del contenedor<br/>(muere con él)"]
>     I --> W
> ```

> [!warning] El fallo nº1: creer que `stop` y `rm` son lo mismo
> **No lo son, y la diferencia es todo:**
>
> | Acción | ¿Sobreviven los datos? |
> |---|---|
> | `docker stop` + `docker start` | ✅ **Sí.** La capa de escritura sigue ahí. |
> | `docker restart` | ✅ **Sí.** |
> | `docker rm` + `docker run` | ❌ **No.** Contenedor nuevo, capa nueva, vacía. |
>
> Mucha gente cree que un contenedor pierde los datos al pararlo. **Es falso.** Los pierde al **borrarlo**. Hoy lo compruebas tú.

> [!example] Vocabulario de esta práctica
> - **Efímero:** que no está pensado para durar. Aplicado aquí: sus datos mueren con él.
> - **Capa de escritura:** la capa propia y modificable de cada contenedor.
> - **Recrear:** borrar un contenedor y levantar otro de la misma imagen. **Aquí es donde se pierden los datos.**
> - **Estado:** los datos que un servicio acumula (ficheros, base de datos, configuración).
> - **Persistencia:** que el estado sobreviva al contenedor. Es la fase B6.4.

## 🛠️ Procedimiento

> [!example] Paso 0 — Prepárate y empieza a grabar
> Arranca OBS y preséntate.
> ```bash
> docker run -d --name efimero nginx
> docker ps
> ```

> [!example] Paso 1 — Escribe algo dentro
> ```bash
> docker exec efimero bash -c 'echo "Datos importantes de la empresa" > /datos_criticos.txt'
> docker exec efimero cat /datos_criticos.txt
> ```
> El fichero existe dentro del contenedor.

> [!example] Paso 2 — Modifica también la web que sirve
> ```bash
> docker exec efimero bash -c 'echo "<h1>Web de Boochan</h1>" > /usr/share/nginx/html/index.html'
> docker exec efimero cat /usr/share/nginx/html/index.html
> ```
> Has cambiado el contenido real del servicio.

> [!example] Paso 3 — PRIMERA PRUEBA: parar y arrancar
> ```bash
> docker stop efimero
> docker start efimero
> docker exec efimero cat /datos_criticos.txt
> docker exec efimero cat /usr/share/nginx/html/index.html
> ```
> **Los datos siguen ahí.** Escríbelo en tu cuaderno y dilo en el vídeo: *"parar no borra"*.
>
> Prueba también `docker restart efimero` y vuelve a comprobarlo. Igual.

> [!example] Paso 4 — SEGUNDA PRUEBA: borrar y recrear
> ```bash
> docker rm -f efimero
> docker run -d --name efimero nginx
> docker exec efimero cat /datos_criticos.txt
> ```
> **`No such file or directory`.**
>
> Comprueba también la web:
> ```bash
> docker exec efimero cat /usr/share/nginx/html/index.html
> ```
> Ha vuelto la página por defecto de Nginx. **Todo lo que escribiste ha desaparecido.**

> [!example] Paso 5 — Entiende por qué, no te limites a verlo
> Explícalo en el vídeo con estas tres frases:
> 1. La **imagen** nunca cambió: sigue intacta, por eso la web volvió a su estado original.
> 2. Lo que escribiste vivía en la **capa de escritura** del primer contenedor.
> 3. `docker rm` borró ese contenedor **y su capa**. El nuevo tiene una capa nueva y vacía.

> [!example] Paso 6 — Compruébalo con la imagen
> ```bash
> docker images nginx
> ```
> Mismo tamaño, misma imagen, sin tocar. **Nada de lo que hiciste la modificó.** Es de solo lectura, y ahora sabes que eso es literal.

> [!example] Paso 7 — Un caso que asusta más
> ```bash
> docker rm -f efimero
> docker run -d --name basedatos -e POSTGRES_PASSWORD=prueba postgres:16
> sleep 20
> docker exec basedatos psql -U postgres -c "CREATE TABLE alumnos (nombre TEXT);"
> docker exec basedatos psql -U postgres -c "INSERT INTO alumnos VALUES ('Marko');"
> docker exec basedatos psql -U postgres -c "SELECT * FROM alumnos;"
> ```
> Tienes una base de datos con un registro. Ahora:
> ```bash
> docker rm -f basedatos
> docker run -d --name basedatos -e POSTGRES_PASSWORD=prueba postgres:16
> sleep 20
> docker exec basedatos psql -U postgres -c "SELECT * FROM alumnos;"
> ```
> **`relation "alumnos" does not exist`.** La tabla y sus datos no existen.
>
> Esto es exactamente lo que le pasó al técnico del caso real. Ya no te va a pasar a ti.

> [!warning] Si te sale `connection refused` o `the database system is starting up`
> **No has hecho nada mal y no es el error que buscamos.** PostgreSQL, la primera vez que arranca, tiene que crear la base de datos entera antes de aceptar conexiones. En una máquina virtual de aula eso puede tardar más de los 20 segundos del `sleep`.
>
> La solución no es esperar a ciegas, es **preguntarle al servicio si ya está listo**:
> ```bash
> docker logs basedatos | tail -5
> ```
> Cuando veas `database system is ready to accept connections`, repite el comando `psql` que te falló y seguirá la práctica con normalidad.
>
> Apréndete este reflejo, porque es de los que más se usan en la vida real: **cuando un servicio no responde, lo primero es mirar sus registros.** Es justo lo que harás en la práctica B6.6.2.

> [!example] Paso 8 — Limpia y cierra
> ```bash
> docker rm -f basedatos
> docker ps -a
> ```
> Detén OBS, nombra el vídeo **`B6.2.3 · El contenedor es efímero`**, súbelo a **`B6_Contenedores`** y añade timestamps.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Creer que `stop` borra los datos | Miedo infundado, se evita parar servicios | Solo `rm` destruye. Compruébalo tú. |
> | Poner datos importantes en un contenedor sin volumen | Pérdida total al recrear | Fase B6.4: volúmenes. |
> | Pensar que la imagen se modifica al escribir dentro | Confusión imagen/contenedor | La imagen es **de solo lectura**. |
> | No esperar a que arranque PostgreSQL | `connection refused` en el Paso 7 | `docker logs basedatos` hasta ver `ready to accept connections`. |
> | Actualizar un servicio con `rm` + `run` sin volumen | **Pérdida de datos en producción** | Nunca recrear un contenedor con estado sin persistencia. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - Has comprobado que tras `stop` + `start` **los datos siguen**.
> - Has comprobado que tras `rm` + `run` **los datos no están**.
> - Sabes explicar la diferencia usando la **capa de escritura**.
> - Has reproducido la pérdida con una base de datos real.

> [!question] Comprueba que lo has entendido
> 1. ¿Sobreviven los datos a `docker stop`? ¿Y a `docker rm`? Explica la diferencia con la capa de escritura.
> 2. ¿Por qué al recrear el contenedor volvió la página por defecto de Nginx?
> 3. La imagen no cambió de tamaño aunque escribiste ficheros dentro. ¿Por qué?
> 4. Un compañero quiere actualizar la versión de PostgreSQL de su contenedor. ¿Qué le adviertes **antes** de que lo haga?
