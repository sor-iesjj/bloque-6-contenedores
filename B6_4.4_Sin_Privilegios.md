## B6.4.4 — Ejecutar un contenedor sin ser root

> [!info] Caso real (contexto profesional)
> Auditoría de seguridad en la empresa. El auditor pregunta: *"¿con qué usuario se ejecutan vuestros contenedores?"*. La respuesta *"con el que venga por defecto"* es un hallazgo de auditoría. **Todos venían como root.** Establecer niveles de seguridad en el acceso a los recursos es literalmente lo que pide el **CE.04.f**.

- **🎯 Objetivo real:** ejecutar servicios en contenedor **sin privilegios de root** y comprobar en la práctica qué se gana.
- **🧩 Problema que resuelve:** un contenedor comprometido corriendo como root es una puerta abierta a tu servidor.

## 📚 Fundamento

> [!warning] Por qué root en el contenedor es un problema de verdad
> Ya sabes tres cosas de este bloque, y juntas dan miedo:
> 1. El contenedor **es un proceso de tu servidor** (B6.2.2).
> 2. Corre **como root por defecto** (B6.4.3).
> 3. Comparte **el kernel** con el anfitrión (B6.0.1).
>
> Consecuencia: si alguien encuentra un fallo en un servicio contenedorizado, obtiene **una sesión de root en un proceso de tu servidor**. Si además ese contenedor tiene montada una carpeta tuya, puede escribir en ella como root. Lo comprobaste ayer sin querer.
>
> **El aislamiento no es una barrera de seguridad total. Es una barrera que hay que reforzar.**

> [!info] Los cuatro niveles de refuerzo, de menos a más
> | Nivel | Qué hace | Coste |
> |---|---|---|
> | 1 · `--user` | El proceso no es root | Ninguno |
> | 2 · `--read-only` | El contenedor no puede escribir en su propio sistema de archivos | Bajo |
> | 3 · `--cap-drop=ALL` | Le quitas las capacidades del kernel que no necesita | Bajo |
> | 4 · `--security-opt=no-new-privileges` | Impide escalar privilegios dentro | Ninguno |
>
> Los cuatro se combinan y **ninguno cuesta rendimiento**. No aplicarlos es simple desconocimiento.

> [!warning] El fallo nº1: `--user` a secas sobre cualquier imagen
> Muchas imágenes están hechas suponiendo que son root: escriben en `/var/run`, `/tmp` o su directorio de trabajo al arrancar. Si les cambias el usuario sin más, **fallan al arrancar** con errores de permisos que despistan mucho.
>
> Nginx es el ejemplo típico: necesita el puerto 80 (puerto privilegiado, <1024) y escribir su PID. Para eso existen **imágenes preparadas para no-root**, como `nginxinc/nginx-unprivileged`, que escuchan en el 8080 y no necesitan privilegios.
>
> **La regla:** si al aplicar `--user` el contenedor no arranca, no fuerces la imagen — busca la variante *unprivileged* o mira su documentación.

> [!example] Vocabulario de esta práctica
> - **`--user UID:GID`:** ejecuta el proceso con esa identidad.
> - **`--read-only`:** sistema de archivos del contenedor en solo lectura.
> - **`--tmpfs`:** memoria escribible para lo imprescindible cuando usas `--read-only`.
> - **Capacidad (*capability*):** permiso concreto del kernel (cambiar la hora, abrir puertos bajos…). Root las tiene todas.
> - **`--cap-drop=ALL`:** se las quitas todas y añades solo las que hagan falta.
> - **Puerto privilegiado:** por debajo del 1024. Solo root puede abrirlos.

## 🛠️ Procedimiento

> [!example] Paso 0 — Prepárate y empieza a grabar
> Arranca OBS y preséntate.
> ```bash
> id
> docker ps -a
> ```

> [!example] Paso 1 — Comprueba el punto de partida
> ```bash
> docker run -d --name inseguro nginx
> docker exec inseguro id
> docker exec inseguro whoami
> ```
> **`uid=0(root)`.** Un servicio web de cara al público, corriendo como root. Este es el estado por defecto de casi todos los servidores.

> [!example] Paso 2 — Demuestra el riesgo con un caso concreto
> ```bash
> mkdir -p ~/datos_empresa
> echo "nomina confidencial" > ~/datos_empresa/nominas.txt
> chmod 600 ~/datos_empresa/nominas.txt
> ls -l ~/datos_empresa
> docker run --rm -v ~/datos_empresa:/datos nginx cat /datos/nominas.txt
> ```
> **Lo lee sin problema**, aunque el fichero sea `600` (solo el propietario). Porque root se salta los permisos.
> ```bash
> docker run --rm -v ~/datos_empresa:/datos nginx sh -c 'echo "MODIFICADO" >> /datos/nominas.txt'
> cat ~/datos_empresa/nominas.txt
> ```
> **También escribe.** Un contenedor comprometido con esa carpeta montada tiene acceso total. Explica la gravedad en el vídeo.

> [!example] Paso 3 — Provoca el fallo de `--user` mal aplicado
> ```bash
> docker rm -f inseguro
> docker run -d --name fallo --user 1000:1000 nginx
> sleep 3
> docker ps -a | grep fallo
> docker logs fallo | tail -10
> ```
> **Falla**, con errores de permisos al escribir su fichero de PID o al abrir el puerto 80.
>
> **No es un error tuyo: es la imagen, que da por hecho que es root.** Aquí es donde mucha gente se rinde y lo deja como estaba.
> ```bash
> docker rm -f fallo
> ```

> [!example] Paso 4 — La solución: imagen preparada para no-root
> ```bash
> docker run -d --name seguro -p 8080:8080 nginxinc/nginx-unprivileged
> docker exec seguro id
> curl -s http://localhost:8080 | head -5
> ```
> **`uid=101`, no root.** Y el servicio funciona.
>
> Fíjate en el puerto: **8080, no 80**, precisamente porque un proceso no-root no puede abrir puertos por debajo de 1024. La imagen está diseñada teniéndolo en cuenta.

> [!example] Paso 5 — Comprueba que ahora NO puede
> ```bash
> docker rm -f seguro
> docker run --rm -v ~/datos_empresa:/datos --user 1000:1000 nginxinc/nginx-unprivileged cat /datos/nominas.txt
> ```
> Si el fichero es `600` y tuyo (UID 1000), lo lee. Prueba con otro UID:
> ```bash
> docker run --rm -v ~/datos_empresa:/datos --user 1500:1500 nginxinc/nginx-unprivileged cat /datos/nominas.txt
> ```
> **`Permission denied`.** El aislamiento ahora **sí** protege el fichero.
>
> **Compara con el Paso 2 y di la diferencia en voz alta.** Es el entregable de la práctica.

> [!example] Paso 6 — Sistema de archivos en solo lectura
> ```bash
> docker run -d --name solo_lectura -p 8080:8080 \
>   --read-only \
>   --tmpfs /tmp \
>   --tmpfs /var/cache/nginx \
>   --tmpfs /var/run \
>   nginxinc/nginx-unprivileged
> sleep 3
> curl -s http://localhost:8080 | head -3
> docker exec solo_lectura sh -c 'echo x > /etc/prueba.txt'
> ```
> El servicio funciona y **no puede modificar su propio sistema de archivos**. Un atacante no puede dejar nada instalado.
>
> Los `--tmpfs` son los huecos escribibles imprescindibles, y viven **en memoria**: desaparecen al parar.

> [!example] Paso 7 — Quitar capacidades
> ```bash
> docker rm -f solo_lectura
> docker run -d --name blindado -p 8080:8080 \
>   --user 101:101 \
>   --read-only \
>   --tmpfs /tmp --tmpfs /var/cache/nginx --tmpfs /var/run \
>   --cap-drop=ALL \
>   --security-opt=no-new-privileges \
>   nginxinc/nginx-unprivileged
> sleep 3
> curl -s http://localhost:8080 | head -3
> docker exec blindado id
> ```
> **Los cuatro niveles a la vez, y el servicio sigue funcionando igual de bien.** Compara con el Paso 1: mismo servicio, riesgo radicalmente distinto, **coste cero**.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | `--user` sobre una imagen que exige root | No arranca, errores confusos | Usa la variante *unprivileged*. |
> | Intentar abrir el puerto 80 sin root | *"permission denied"* | Puertos <1024 son privilegiados: usa 8080 y publica en el que quieras. |
> | `--read-only` sin `--tmpfs` | El servicio no arranca | Añade los huecos escribibles necesarios. |
> | Usar `--privileged` para que "funcione" | Anulas **todo** el aislamiento | Nunca. Si lo ves en una guía, desconfía. |
> | Montar carpetas sensibles en contenedores root | Acceso total a esos datos | `--user` + montar solo lo necesario + `:ro`. |
> | Aplicar esto solo en producción | Pruebas y producción divergen | Aplícalo desde el laboratorio. |
