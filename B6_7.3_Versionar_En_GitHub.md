> [!warning] Última práctica del bloque y del módulo
> Aquí no aprendes ninguna herramienta nueva. Coges **el trabajo de las siete fases** y lo dejas de una forma que otra persona pueda usarlo sin ti.
>
> Y hay una prueba que separa un proyecto de verdad de una carpeta con ficheros sueltos: **clonarlo en un sitio limpio y que levante a la primera**. Eso es lo que se evalúa hoy.

> [!info] Caso real (contexto profesional)
> Terminas las prácticas en la empresa y te vas. El servicio que montaste sigue corriendo. Seis meses después hay que moverlo a otro servidor y **tú ya no estás**.
>
> Si dejaste un repositorio con el `compose.yaml` y un `README` decente, se resuelve en diez minutos. Si dejaste el servicio corriendo y nada más, alguien va a pasar dos días haciendo ingeniería inversa a tu trabajo. **Las dos cosas se recuerdan en una empresa. Solo una es buena.**

- **🎯 Objetivo real:** versionar el proyecto, documentarlo y **demostrar que se levanta desde cero clonando el repositorio**.
- **🧩 Problema que resuelve:** un servicio que no está documentado ni versionado **no es reproducible**, y por tanto no es profesional.

## 📚 Fundamento

> [!info] Qué va al repositorio y qué no
> La regla se dice en una frase: **al repositorio va la receta, nunca el resultado ni las llaves.**
>
> | ✅ Sí va | ❌ No va |
> |---|---|
> | `compose.yaml` | Contraseñas, tokens, claves (`.env`) |
> | `README.md` con las instrucciones | Datos de los volúmenes |
> | Contenido del sitio (`sitio/`) | Registros (`*.log`) |
> | `.gitignore` | Imágenes de Docker |
> | `.env.example` (**sin** valores reales) | Nada que pese cientos de MB |
>
> Esto es exactamente lo que trabajaste en la Fase 0: el repositorio guarda **lo que hace falta para reconstruir**, no lo reconstruido.

> [!warning] El fallo nº1: subir contraseñas al repositorio
> Un `docker-compose` real lleva credenciales: la contraseña de la base de datos, una clave de API. Se ponen en un fichero `.env`, **y ese fichero jamás se sube**.
>
> Y ojo con la parte que casi nadie sabe: **borrar el fichero después no arregla nada**. Git guarda el historial completo: la contraseña sigue ahí, en el *commit* anterior, a la vista de todo el mundo.
>
> Si subes una credencial por error, **la contraseña está quemada y hay que cambiarla**. No hay atajo. Por eso el `.gitignore` se escribe **antes** del primer `commit`, no después.

> [!info] La prueba de fuego: reproducibilidad
> Tu proyecto está bien si un desconocido puede hacer esto y funciona:
>
> ```bash
> git clone <tu-repo>
> cd <carpeta>
> docker compose up -d
> ```
>
> **Tres comandos.** Si hace falta algo más y no está en el `README`, el proyecto no está terminado. Hoy lo vas a comprobar tú mismo, sobre tu propio repositorio.

> [!example] Vocabulario de esta práctica
> - **Reproducible:** que se puede reconstruir desde cero a partir del repositorio, sin conocimiento oculto.
> - **`.gitignore`:** lista de lo que Git debe ignorar. **Se escribe primero.**
> - **`.env`:** fichero de variables con datos sensibles. Nunca se versiona.
> - **`.env.example`:** la plantilla, con los nombres de las variables y **sin** los valores.
> - **`README.md`:** la puerta de entrada. Si no está, el repositorio es un montón de ficheros.

## 🛠️ Procedimiento

> [!example] Paso 0 — Prepárate y empieza a grabar
> Arranca OBS en el servidor y preséntate.
> ```bash
> cd ~/proyecto-b6
> ls -a
> docker compose ps
> git --version
> ```

> [!example] Paso 1 — El `.gitignore`, ANTES de nada
> ```bash
> nano .gitignore
> ```
> ```gitignore
> # Secretos: jamás al repositorio
> .env
>
> # Datos y registros generados
> datos/
> *.log
>
> # Basura del sistema
> .DS_Store
> Thumbs.db
> ```
> Guarda y **explica en el vídeo por qué este fichero va primero**: porque después del primer `commit` ya es tarde para lo que se haya colado.

> [!example] Paso 2 — Saca los datos sensibles del `compose.yaml`
> Aunque tu proyecto de hoy no tenga contraseñas, se hace bien desde el principio:
> ```bash
> echo "PUERTO_WEB=80" > .env
> echo "PUERTO_WEB=80" > .env.example
> ```
> Y en `compose.yaml` usa la variable:
> ```yaml
>     ports:
>       - "${PUERTO_WEB}:80"
> ```
> Comprueba que la sustitución funciona **antes** de levantar nada:
> ```bash
> docker compose config | grep -A2 ports
> docker compose up -d
> curl -s -o /dev/null -w "%{http_code}\n" http://localhost
> ```
> El `.env` real se queda en tu servidor; el `.env.example` es el que ve todo el mundo, con el nombre de la variable y sin secretos.

> [!example] Paso 3 — Escribe el `README.md`
> ```bash
> nano README.md
> ```
> Tiene que contestar a cinco preguntas, ni una menos:
> ```markdown
> # Intranet en contenedor — Bloque 6 (SOR)
>
> Servicio web en contenedor para el dominio BOOCHANLAB.LOCAL.
> Autor: <tu nombre> · 2.º SMR · IES Jorge Juan
>
> ## Qué hace
> Publica una intranet estática accesible desde los clientes Windows del dominio.
>
> ## Requisitos
> - Ubuntu Server con Docker Engine y el complemento Compose.
> - Puerto 80 libre y abierto en el cortafuegos.
> - Registro DNS `intranet` apuntando a la IP del servidor.
>
> ## Cómo se levanta
> ```bash
> cp .env.example .env     # y ajusta el puerto si hace falta
> docker compose up -d
> ```
>
> ## Cómo se comprueba
> - Servidor: `curl http://localhost`
> - Cliente Windows: `http://intranet.boochanlab.local`
> - Registros: `docker compose logs -f web`
>
> ## Cómo se retira
> ```bash
> docker compose down       # -v borra ADEMÁS los volúmenes
> ```
> ```
> **Qué hace, qué necesita, cómo se levanta, cómo se comprueba y cómo se retira.** Un `README` sin las cinco no vale.

> [!example] Paso 4 — El primer *commit*
> ```bash
> git init -b main
> git add .
> git status
> ```
> **Párate aquí y lee la lista con calma.** ¿Aparece `.env`? Entonces el `.gitignore` está mal y hay que arreglarlo **ahora**, no después.
> ```bash
> git commit -m "Intranet en contenedor: compose, documentacion y variables"
> git log --oneline
> ```

> [!example] Paso 5 — Súbelo a GitHub
> Crea el repositorio **vacío** en GitHub (sin README, para que no choque) y:
> ```bash
> git remote add origin git@github.com:<tu-usuario>/intranet-b6.git
> git push -u origin main
> ```
> Usas la clave SSH de la **Fase 0.2**. Si te pide contraseña, es que está tirando de HTTPS: revisa la URL del `remote`.
>
> Abre el repositorio en el navegador y **comprueba que `.env` NO está**. Enséñalo en el vídeo.

> [!example] Paso 6 — La prueba de fuego (el corazón de la práctica)
> Ahora demuéstralo. Clona **en una carpeta limpia**, como haría otra persona:
> ```bash
> cd /tmp
> git clone git@github.com:<tu-usuario>/intranet-b6.git prueba-limpia
> cd prueba-limpia
> ls -a
> ```
> Fíjate: **no hay `.env`**. Un desconocido tendría que crearlo — y tu `README` se lo dice.
> ```bash
> cp .env.example .env
> sed -i 's/PUERTO_WEB=80/PUERTO_WEB=8081/' .env
> docker compose up -d
> curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8081
> ```
> **`200`.** Acabas de levantar el servicio entero **desde el repositorio, en otra carpeta, sin tocar el original**. Eso es reproducibilidad, y es lo que se te evalúa.
>
> Recoge la prueba:
> ```bash
> docker compose down
> cd /tmp && rm -rf prueba-limpia
> ```

> [!example] Paso 7 — Un cambio, un *commit* que se entienda
> Modifica algo del sitio:
> ```bash
> cd ~/proyecto-b6
> echo "<p>Actualizado el $(date +%d/%m/%Y)</p>" >> sitio/index.html
> git diff
> git add sitio/index.html
> git commit -m "Anadir fecha de actualizacion a la intranet"
> git push
> ```
> **Mira el `git diff` en el vídeo antes de confirmar.** Es la costumbre que separa a quien versiona de quien acumula ficheros.

> [!example] Paso 8 — Etiqueta la entrega
> ```bash
> git tag -a entrega-b6 -m "Entrega del Bloque 6"
> git push origin entrega-b6
> ```
> La etiqueta marca **el estado exacto que entregas**, aunque sigas tocando el repositorio después.

> [!example] Paso 9 — Repaso final del bloque (en el vídeo)
> Con el `compose.yaml` en pantalla, recorre el bloque entero en dos minutos:
>
> | Línea del fichero | De dónde sale |
> |---|---|
> | `image:` | B6.1.4 — imágenes y etiquetas |
> | `ports:` | B6.3.2 — publicar puertos |
> | `volumes:` | B6.4.1 y B6.4.2 — persistencia |
> | `mem_limit:` | B6.6.1 — *cgroups* |
> | `logging:` | B6.6.2 — registros |
> | `restart:` | B6.7.2 — que siga vivo el lunes |
>
> **Veintitantas líneas de fichero para veintidós horas de bloque.** Ese es el resumen honesto de lo que has aprendido.

> [!example] Paso 10 — Limpia y cierra
> ```bash
> docker compose ps
> git status
> ```
> Deja el servicio levantado y el repositorio limpio.
>
> Detén OBS, nombra el vídeo **`B6.7.3 · Versionar el proyecto en GitHub y entregar`**, súbelo a **`B6_Contenedores`** y añade timestamps.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Escribir el `.gitignore` después del primer `commit` | Lo que se coló ya está en el historial | `.gitignore` **primero**, siempre. |
> | Subir el `.env` | Credenciales públicas; hay que cambiarlas todas | `git status` antes de cada `commit`. |
> | Creer que borrar un fichero lo quita del historial | La contraseña sigue accesible en Git | Si se sube, **se cambia la credencial**. |
> | `README` sin cómo levantar el servicio | Nadie puede usarlo, ni tú en seis meses | Las cinco preguntas del Paso 3. |
> | Mensajes de *commit* tipo "cambios" o "asdf" | El historial no sirve para nada | Qué se cambió y por qué. |
> | Subir volúmenes o registros | Repositorio enorme e inútil | Van en el `.gitignore`. |
> | No probar el clonado limpio | Descubres que falta algo cuando ya es tarde | **El Paso 6 no es opcional.** |

> [!success] ✅ Verificación: ¿está bien hecho?
> - El repositorio está en GitHub y **`.env` no aparece** en él.
> - El `README.md` responde a las cinco preguntas.
> - `git clone` en carpeta limpia + `docker compose up -d` **levanta el servicio**.
> - Hay al menos **dos *commits*** con mensajes que se entienden.
> - La entrega está etiquetada.
> - El servicio original sigue accesible desde el cliente Windows por su nombre.

> [!question] Comprueba que lo has entendido
> 1. Con tus palabras: ¿qué significa que un proyecto sea *reproducible* y qué comando lo demuestra?
> 2. ¿Por qué el `.gitignore` se escribe antes del primer `commit` y no después?
> 3. Has subido por error la contraseña de una base de datos y la has borrado en el *commit* siguiente. ¿Estás a salvo? Explica por qué.
> 4. ¿Qué diferencia hay entre `.env` y `.env.example`, y por qué uno se sube y el otro no?
> 5. Alguien clona tu repositorio dentro de un año. Repasa tu `README` y di si le falta algo para arrancar sin preguntarte nada.
> 6. Cita **tres** líneas de tu `compose.yaml` y di de qué práctica del bloque salió cada una y qué problema resolvía.
