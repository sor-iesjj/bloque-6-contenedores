## B6.1.3 — Ciclo de vida: `run`, `ps`, `stop`, `start`, `rm`

> [!abstract] Ficha de la práctica

> - **Bloque 6** (Aislamiento de servicios) · **Fase B6.1** (Primer contacto) · **Nivel 1** (Básico) · **RA.01 · RA.05** · **CE.01.b · CE.05.f**
> - **🎬 Playlist:** `B6_Contenedores`

> - **Requisito previo:** [[B6_1.2_Primer_Contenedor|B6.1.2]].

> [!info] Caso real (contexto profesional)
> En el servidor de la empresa hay catorce contenedores. Tres están parados, dos fallan al arrancar y nadie sabe cuáles se pueden borrar porque todos tienen nombres inventados como `nostalgic_hopper`. Administrar contenedores **es administrar su ciclo de vida**: saber en qué estado está cada uno, moverlo entre estados y limpiar lo que sobra.

- **🎯 Objetivo real:** dominar los estados de un contenedor y los comandos que lo mueven entre ellos, usando un servicio que **no termina solo** (Nginx).
- **🧩 Problema que resuelve:** sin control del ciclo de vida acabas con decenas de contenedores zombis ocupando disco y sin saber cuál es cuál.

---

## 📚 Fundamento

> [!info] Los cuatro estados y los comandos que los conectan
> Un contenedor está siempre en uno de estos estados. **Los comandos son las flechas.**
>
> ```mermaid
> stateDiagram-v2
>     [*] --> Created: docker create
>     Created --> Running: docker start
>     [*] --> Running: docker run
>     Running --> Exited: docker stop
>     Exited --> Running: docker start
>     Running --> Running: docker restart
>     Exited --> [*]: docker rm
> ```
>
> **Lo importante:** de `Exited` se puede **volver**. `stop` no destruye nada: el contenedor sigue ahí con su capa de escritura intacta. El único comando que destruye es **`rm`**.

> [!warning] El fallo nº1: `hello-world` no sirve para aprender esto
> `hello-world` termina solo en un segundo. No puedes practicar `stop` sobre algo que ya se ha parado.
>
> **Por eso aquí usamos Nginx**, que es un servidor web: arranca y **se queda escuchando indefinidamente**. Es el comportamiento normal de un servicio y el que te vas a encontrar en el mundo real.
>
> Aviso: en esta práctica Nginx funciona pero **no podrás acceder a él desde el navegador**. Eso es la fase B6.3 y tiene su explicación. Aquí solo nos interesa que se mantenga vivo.

> [!example] Vocabulario de esta práctica
> - **`-d` (*detached*):** arranca el contenedor en segundo plano y te devuelve el terminal.
> - **`--name`:** le pones tú el nombre en vez de aceptar el inventado. **Imprescindible** para administrar.
> - **`Up 3 minutes`:** lleva 3 minutos en marcha.
> - **`Exited (137)`:** lo mataron. El 137 significa que recibió un `SIGKILL`.
> - **`docker rm -f`:** para y borra de un golpe. Cómodo y peligroso.

## 🛠️ Procedimiento

> [!example] Paso 0 — Prepárate y empieza a grabar
> Arranca OBS y preséntate. Deja el terminal limpio: `clear`.

> [!example] Paso 1 — Arranca un servicio de verdad
> ```bash
> docker run -d --name web1 nginx
> docker ps
> ```
> Ahora **sí** aparece en `docker ps`, con estado `Up`. Diferencia clave con `hello-world`: Nginx no termina, se queda escuchando.
>
> El identificador largo que te devuelve el `run` es el **ID del contenedor**. Puedes usar sus primeros caracteres en cualquier comando, pero para eso está `--name web1`.

> [!example] Paso 2 — Párala y compruébalo
> ```bash
> docker stop web1
> docker ps
> docker ps -a
> ```
> Desaparece de `docker ps` y aparece en `docker ps -a` como `Exited (0)`. **No lo has borrado.** Sigue existiendo.

> [!example] Paso 3 — Arráncala de nuevo
> ```bash
> docker start web1
> docker ps
> ```
> Vuelve a estar `Up`. **Es el mismo contenedor**, no uno nuevo: conserva su ID, su nombre y todo lo que hubiera escrito dentro.
>
> Compara: `docker start` reanuda uno existente · `docker run` **crea uno nuevo**. Confundirlos es el origen de la mitad de los contenedores basura de un servidor.

> [!example] Paso 4 — Reinicia
> ```bash
> docker restart web1
> docker ps
> ```
> Fíjate en la columna `STATUS`: el contador vuelve a empezar (`Up 2 seconds`). Equivale a `stop` + `start` en un solo comando.

> [!example] Paso 5 — Demuestra que `run` crea uno nuevo
> ```bash
> docker run -d --name web2 nginx
> docker ps
> ```
> **Dos contenedores en marcha, de la misma imagen.** Comprueba que la imagen sigue siendo una sola:
> ```bash
> docker images
> ```

> [!example] Paso 6 — Intenta borrar uno en marcha
> ```bash
> docker rm web2
> ```
> **Falla a propósito.** Docker te protege de destruir algo que está funcionando. La forma correcta:
> ```bash
> docker stop web2
> docker rm web2
> docker ps -a
> ```
> `web2` ha desaparecido de la lista. **Ahora sí lo has destruido.**

> [!example] Paso 7 — El atajo, y por qué hay que tenerle respeto
> ```bash
> docker rm -f web1
> docker ps -a
> ```
> `-f` (*force*) para y borra de un golpe. Es cómodo, pero **te salta la red de seguridad del Paso 6**: si te equivocas de nombre, destruyes un servicio en marcha sin aviso ninguno. Úsalo cuando sepas exactamente qué estás borrando.

> [!example] Paso 8 — Interpreta la salida como un administrador
> ```bash
> docker run -d --name web3 nginx
> docker ps -a --format "table {{.Names}}\t{{.Image}}\t{{.Status}}"
> docker inspect --format '{{.State.Status}}' web3
> ```
> El último comando devuelve el estado en una sola palabra: útil para scripts y para automatizar comprobaciones.

> [!example] Paso 9 — Limpia y cierra
> ```bash
> docker rm -f web3
> docker ps -a
> ```
> Deja el sistema sin contenedores. Detén OBS, nombra el vídeo **`B6.1.3 · Ciclo de vida de un contenedor`**, súbelo a **`B6_Contenedores`** y añade timestamps.

## 🚩 Errores y verificación

> [!warning] Errores típicos (evítalos)
> | Error | Qué pasa | Cómo evitarlo |
> | :--- | :--- | :--- |
> | Usar `run` cuando querías `start` | Se crean contenedores duplicados sin parar | `run` = nuevo · `start` = reanudar uno existente. |
> | No poner `--name` | Nombres inventados, imposible administrar | Nombra **siempre** tus contenedores. |
> | Olvidar `-d` con Nginx | El terminal se queda bloqueado | `-d` lo manda a segundo plano. Sal con `Ctrl+C` y repite. |
> | `docker rm` sobre uno en marcha | Falla con *"container is running"* | Primero `stop`, luego `rm`. |
> | Abusar de `rm -f` | Destruyes servicios vivos por error | Resérvalo para cuando sepas qué borras. |
> | Creer que `stop` borra | Se acumulan contenedores parados | `stop` para · **solo `rm` destruye**. |

> [!success] ✅ Verificación: ¿está bien hecho?
> - Sabes mover un contenedor entre `Running` y `Exited` en los dos sentidos.
> - Explicas la diferencia entre `run` y `start` sin dudar.
> - Has visto fallar `docker rm` sobre un contenedor en marcha y sabes por qué.
> - `docker ps -a` queda **vacío** al terminar la práctica.
> - Sabes leer la columna `STATUS` (`Up`, `Exited (0)`, `Exited (137)`).

> [!question] Comprueba que lo has entendido
> 1. Dibuja de memoria el diagrama de estados con los comandos en las flechas.
> 2. Diferencia entre `docker stop` y `docker rm`. ¿Cuál se puede deshacer?

> 4. Ejecutas `docker run -d --name web1 nginx` dos veces seguidas. ¿Qué ocurre la segunda vez y por qué?

> 6. Un compañero tiene 30 contenedores `Exited` en su servidor. ¿Cómo ha llegado a esa situación y qué le recomiendas?
